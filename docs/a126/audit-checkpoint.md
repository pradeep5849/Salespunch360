# A126 — Review Account package

Date: 12 November 2026 (Asia/Kolkata). Route: `/workspace/billing/checkout/account`. Audit only; keep current UI. No application code, production billing data, prices, orders, payments, messages or subscription activation changed. Mocked order/email delegates do not send actual notifications or create real purchases.

## Existing safeguards

The page invokes the authorized billing dashboard, rejects missing Account capability and redirects Plus to the combined billing flow. Quantity after normalization must be 1–100. The edit/review form uses GET; online payment is clearly disabled/Coming Soon. Manual submission calls mutationGuard, requires MANUAL, validates the period and delegates to createAccountPackageOrder, which checks billing authority/edition and strict integer quantity before creating a pending order under a company lock. Pending redirect occurs after the service returns; it does not declare payment or activation success. Server-side rate snapshots and immutable existing orders must be preserved in any correction.

## Findings (OPEN)

- **A126-F01 — fixed checkout prices diverge from authoritative order prices (Medium).** The page computes unit/total using ACCOUNT_PACKAGE_SIX_MONTH_PRICE_INR/YEARLY constants, ignoring configured rates even when billingDashboard supplies them. In a synthetic fixture with six-month rate 900, a two-package review displays 800 instead of 1800, while the actual order service reads the configured rate. This is a distinct display layer from A124-F01's missing Account-only loader query: fixing the loader alone will not repair this page. Use the same authoritative effective quote in review and bind/revalidate that reviewed intent at submission; explicitly handle changed quotes. No production rate or actual charge was tested.
- **A126-F02 — unrelated pending selection silently reused (Medium).** reusablePendingOrder chooses the latest eligible pending ACCOUNT_PACKAGE order by company/provider, without matching requested package quantity, period or reviewed price. A service probe requesting three six-month packages returned an existing one-package yearly order and created no replacement. Identical-intent reuse also passed, so safe deduplication should remain. Show the pending request and explicitly offer resume/change/cancel according to a reviewed policy; do not silently substitute or overwrite its financial snapshots. This test demonstrates mismatched pending intent, not duplicate payment or unauthorized activation.
- **A126-F03 — review inputs silently normalized (Low).** Math.trunc converts quantity=1.9 to 1 before the integer check, and any period except YEARLY becomes SIX_MONTH. Render probes confirm both; service submission rejects fractional quantity and unsupported period when supplied directly. Invalid 0/101/NaN review quantities are redirected correctly. Validate explicit unsupported/fractional values before normalization and explain correction without silently changing purchase intent. Normal omitted-input defaults can remain intentional. No payment validation bypass was demonstrated.
- **A126-F04 — useful validation failures become generic feedback (Low).** The account action's error allowlist omits INVALID_ACCOUNT_PACKAGE_QUANTITY and INVALID_BILLING_PERIOD. A synthetic quantity rejection redirects to the billing hub with ORDER_CREATE_FAILED, losing the specific explanation and in-page selection context. Rate limiting remains correctly identified, and denied guards prevented both order creation and notification in the probe. Map safe validation codes to actionable feedback while keeping logs sanitized and avoiding success on errors. No notification-delivery certificate is claimed.
