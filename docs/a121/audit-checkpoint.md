# A121 — Attendance (Sales / Field Sales)

Date: 11 November 2026 (Asia/Kolkata). Route: `/workspace/attendance`. Audit uses the current UI, as requested; no external design/reference is required at this checkpoint. Full-app audit includes Sales, Account and shared features. No application implementation, production attendance start/stop, location upload, hosting change or deployment was performed.

## Owner requirement

When a start/end operation is confirmed, show **Attendance started successfully** / **Attendance stopped successfully**, with the confirmed time in IST. Pending, failed and uncertain responses must not claim success. Preserve the current attendance state until the server confirms it; reconcile uncertain submissions without creating duplicate sessions. This is an audit acceptance requirement, not a statement that messaging has been implemented.

## Findings (all OPEN)

- **A121-F01 — confirmed success feedback missing (Medium).** Web AttendanceControls refreshes on ok:true, without setting an explicit started/stopped success message. Both hook probes reproduce this. Native MainViewModel updates attendance state/calls onSuccess, but does not set the requested success message; drawer/card local messages describe obtaining a location rather than confirming the server save. Implement the owner messages with authoritative timestamp and accessible announcement, retained through refresh; failure/uncertain outcomes need distinct wording.
- **A121-F02 — multi-branch start cannot select a branch (Medium).** startAttendance requires resolveWriteBranch, which rejects more than one permitted branch if requestedBranchId is absent. Web AttendanceControls and startAttendanceAction send only location, and the screen supplies no attendance branch selector. A service probe with a current selected-branches principal and two permitted IDs reproduces BRANCH_REQUIRED before any attendance creation. Retain explicit authorized branch selection/context in the request and show a useful error. Native request branch propagation was not fully tested; do not infer a matching native defect solely from this web reproduction.
- **A121-F03 — location requirements conflated (Medium).** The web page passes gpsTrackingEnabled OR attendanceGeofenceEnabled as one gpsEnabled flag. Controls then start a watch and request a fresh location for both start and stop. In geofence-only configuration, the start legitimately needs location, but uploads are rejected by uploadLocationPoint with GPS_DISABLED and backend endAttendance does not require that geofence location. A denial probe shows the UI refuses to send stop when location permission is denied. Native drawer/card also obtains precise location before either action irrespective of the two settings. Separate geofence-at-start, ongoing tracking and stop-location policy; test all four settings combinations and permission revocation. Source/hook evidence only; no real GPS/device run.
- **A121-F04 — transient transport/GPS failure recovery (Medium).** submit does not catch rejected server-action transport promises; a synthetic disconnect rejects without a local error/result message. The upload promise similarly lacks a rejection handler. Any resolved upload ok:false sets trackingStopped=true; the component exposes no reset/retry, and a subsequent render does not start the watch again. Probes reproduce submission rejection and stopped tracking after one rejected GPS result. Handle network uncertainty explicitly, retry/queue only when safe, provide recoverable tracking controls and never leave GPS-active text after an unacknowledged upload. Existing THROTTLED handling remains valid.
- **A121-F05 — inconsistent attendance timezone (Low).** Employee start time in web controls uses browser-default timezone; team page explicitly uses Asia/Kolkata and an IST label. Native formatAttendanceTime uses systemDefault. A non-India device can therefore show different times for the same attendance. Use the agreed IST timestamp consistently, or clearly label any intentional local-zone display. Source-confirmed; no timezone-emulated browser/device run.
- **A121-F06 — team status freshness/empty state (Low).** Team overview is a server-rendered snapshot with no timestamp, page refresh control or polling; it only appears when rows are nonempty. Empty assigned-team/filtered-branch results produce no explanatory team section. Supervisors may mistake an old Working/Not working snapshot for current status. Label last refresh, add refresh/revalidation and clear empty/error states without widening assigned-team/company scope. Source review only; no multi-user live test.
