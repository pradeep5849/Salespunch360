# A120 — Verify my data

Date: 11 November 2026 (Asia/Kolkata). Route: `/workspace/account/utilities/verification`. Audit only; no application code, production data, security settings or scheduler settings changed.

## Approved target and reference

The owner accepted a read-only consistency checker for document totals, payments/allocations, journal balance, stock reconciliation, record/company/branch links and locked-period anomalies, with per-check results, affected records and next steps. It must not claim external bank/cash/physical-stock verification or automatically rewrite history. The supplied reference image shows a success dialog; it does not establish the reference product's internal algorithms.

## Existing implementation

`verifyAccountDataForActor` returns ten checks: journal debit/credit equality; document balance bounds; duplicate system keys; money-account ledger mapping presence; positive stock quantities/reference presence; transfer type pairing; tax-component sum; Project branch/customer company membership; Asset branch membership; assignment-history consistency. It queries eleven company-scoped read sources and calculates results in memory. Web renders status cards, recommendations and at most five sample identifiers. Native receives the results through mobileUtilities but uses the generic JsonList rendering.

## Findings

1. **A120-F01 — branch/role scope mismatch (Medium, OPEN).** Web verifyAccountData authorizes ACCOUNT_REPORTS, then passes only user ID/company ID to the company-wide checker. A selected-branch Accountant is allowed by the actual permission policy; journal queries contain companyId only, without branch scope. The synthetic web-service probe returned OTHER-BRANCH-JV as a sample. This is intra-company branch-scope exposure, not demonstrated cross-company or anonymous access. Native and Utilities menu use ACCOUNT_SETTINGS instead, so direct web access and menu/native policy differ. Restrict company-wide verification to the appropriate all-branch administrator, or implement consistent record/branch/Project scope and label it. Test denied roles and other-branch samples. No live restricted-user request was made.
2. **A120-F02 — incomplete approved reconciliation coverage (Medium, OPEN).** The service does not query payment allocation/advance totals, document lines and discount calculations, stock balances/opening-versus-movement reconciliation, or period locks/entry dates needed to detect lock anomalies. Checking document balance bounds, stored tax-component sums and positive movements does not implement those reconciliations. Add explicit independent checks with authoritative snapshots/effective posting policy, or display them as not checked. Do not imply bank-statement/physical-stock truth.
3. **A120-F03 — transfers can falsely pass (Medium, OPEN).** Pairing groups by sourceId and requires only both movement type names. A synthetic TRANSFER_IN of one unit of p1 and TRANSFER_OUT of 99 units of p2 with the same sourceId returns PASS. Product, quantity equality, warehouse/branch direction and duplicate leg cardinality are not reconciled. Use the transfer model's actual per-line/unit policy; multiple-line transfers require grouped quantities rather than blindly enforcing two rows globally. Include mismatch/duplicate/valid multiline cases.
4. **A120-F04 — system-ledger presence is not checked (Low, OPEN).** groupBy(systemKey) detects duplicate existing keys but no missing required canonical key. An empty system-ledger fixture returns PASS for System ledgers are unique. Uniqueness itself is correctly vacuously true; this is a coverage/initialization gap if treated as complete ledger-integrity verification. Distinguish not initialized/no applicable records from checked canonical readiness, using the company's required account policy rather than hardcoded assumptions.
5. **A120-F05 — result presentation/actionability (Low, OPEN).** Native verification falls through to generic JsonList, showing serialized check objects instead of status, affected records and recommendations as purpose-built fields. Web samples are plain identifiers without authorized detail navigation; neither surface provides a complete/not-checked summary or completed-at/scope context. Recommendations can imply corrective workflows without proving that the actor has access. Provide clear checked scope, applicable/unsupported states and safe links; do not copy the reference's unconditional all-data-matches claim.
6. **A120-F06 — unbounded and non-snapshot scan (Medium, OPEN).** Full-company tables and nested journal lines are loaded without aggregation/chunking; asset checking repeatedly scans assignment and user arrays. Independent reads are not wrapped in a consistent read snapshot in the ordinary web/mobile entrypoints, so concurrent writes can produce misleading transient mismatches. Close-books calls use their own transaction and must be considered separately. Use bounded complete scanning/aggregation and a consistent read strategy; do not truncate and then declare all data checked. Large-company latency/memory and concurrent-write behavior were not benchmarked in this audit.

## Executed probes

Seven mocked/pure-policy probes passed, zero failed/skipped. They observe current behavior rather than asserting every approved requirement works: ten-check/read-only baseline, known journal/tax detection, false-pass transfer mismatch, selected-branch web scope loss, empty-ledger PASS, five-sample cap with retained count, and actual Accountant report permission. All test data was synthetic; no database or network mutation was used. Probe source and raw output are retained as text so they are not added to normal application CI accidentally.

The company filter was present on all mocked read queries. No mutation method was supplied to the checker and the probes completed. This supports a read-only observation for the exercised path, not a full system security certificate. No physical Android run, production data verification, browser interaction/performance run, or exhaustive reference parity was performed. Findings remain OPEN and need separately authorized implementation.
